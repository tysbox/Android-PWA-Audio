## 1. 策定の背景と基本方針

本システムは、P0（バックグラウンド再生・ギャップレス先読み連携・OOM防止）、P1（スレッドプール適正化・バンドルコード分割・ゼロアロケーション・LRUキャッシュ）、P2（Java旧DSP削除・ProGuard/R8整備）のリファクタリングを完了し、**コードの健全性、メモリ効率、動作安定性が大幅に向上** しました。

この強固になった基盤の上で、さらなるプロダクト価値向上を図るため、以下の2つの軸で改善計画を策定します：

1. **アプローチ ①: 非破壊的・即効性重視（既存機能を損なわずに速度・精度UP）**
   - 既存のアーキテクチャ・ファイル構成を崩すことなく、計算効率・応答性・操作性を確実に底上げする施策。
2. **アプローチ ②: 構造転換・劇的進化（次世代ハイエンドオーディオ化）**
   - 多少の構造変更を伴うが、専用高級 DAP（デジタルオーディオプレーヤー）と同等以上の超低遅延・高音質・鉄壁の安定性を手に入れる抜本的施策。

## 2. アプローチ ①: 既存機能を損なわずに速度・精度を高める対策

```
┌────────────────────────────────────────────────────────────────────────┐
│  アプローチ ①: 非破壊的・即効性重視（既存機能を損なわずに速度・精度UP） │
├────────────────────────────────────────────────────────────────────────┤
│  1. RateConverter 多項式事前展開テーブル化 (Polyphase FIR / Hermite)   │
│  2. メタデータ＆アートワークのディスク永続化 (DiskLruCache / Room)     │
│  3. UPnP/DLNA サーバー探索のローカルキャッシュ＆即時表示              │
│  4. Canvas 2D による VUメーター描画ループの React 分離 (60fps化)       │
│  5. USB DAC 出力段のオートパケットプランニング                         │
└────────────────────────────────────────────────────────────────────────┘
```

### 2.1 `RateConverter` の多項式事前展開テーブル化（CPU負荷 40〜60% 削減）
- **現状**:
  `RateConverter.java` は全サンプルに対し、1サンプルごとに Catmull-Rom スプライン補間の3次多項式係数（$a_0, a_1, a_2, a_3$）を逐次展開・乗加算しています。
- **改善手法**:
  小数部 `posFrac`（$0.0 \le f < 1.0$）を 256〜512 段のルックアップテーブル（Polyphase FIR 補間係数テーブル）として静的配列に事前計算。サンプル変換時はインデックス参照と積和のみで完了させます。
- **効果とリスク**:
  - **効果**: 音響的特性（線形位相、ゼロプリリンギング、周波数レスポンス）を **100% 完全に維持** したまま、Java スレッドの計算負荷を半減。発熱とバッテリー消費を大幅抑制。
  - **リスク**: **極小**（既存の `SeamAudit` およびユニットテストでビット単位の出力を検証可能）。

### 2.2 メタデータ＆アルバムアートのディスク永続化（DiskLruCache / SQLite）
- **現状**:
  `LruCache`（メモリ100件）によりセッション内の重複リクエストは抑制されましたが、アプリ再起動時に揮発します。
- **改善手法**:
  Android のキャッシュディレクトリ配下に `DiskLruCache` または軽量 SQLite テーブルを導入。MusicBrainz のクレジット情報や抽出されたアルバムアート画像を永続化します。
- **効果とリスク**:
  - **効果**: 一度聴いたアルバムや楽曲は、次回以降 **オフライン・機内モードでも即座に Wiki / クレジット / アートが表示** される（体感 0ms 表示）。外部 API のレート制限（503）とも完全に無縁化。
  - **リスク**: **極小**（ネットワーク取得成功時のみキャッシュ書き込み、失敗時は既存フォールバック）。

### 2.3 UPnP / DLNA サーバー探索の「即時表示 ＋ バックグラウンド更新」
- **現状**:
  UPnP ブラウザを開くたびに M-SEARCH（マルチキャスト）を発行するため、サーバーがリスト表示されるまでに 1〜3 秒の待機時間が発生します。
- **改善手法**:
  直近で正常接続できたサーバー情報（UUID、名前、BaseURL）を `localStorage` に保持。モーダルが開いた **0ms で前回のサーバーを即時レンダリング** し、裏で M-SEARCH を行いながら死活状態をインクリメンタルに更新します。
- **効果とリスク**:
  - **効果**: NAS 上の音源選択時のもたつきが解消し、ネイティブアプリ同等のレスポンスを獲得。
  - **リスク**: **極小**（サーバー消失時はクリック時に接続エラーハンドリングで検知可能）。

### 2.4 VU メーター描画ループの React 脱却（Canvas 2D / 60fps スムーズ化）
- **現状**:
  100ms ごとに届く `playbackTime` イベントで React の State 更新を行い、SVG / CSS の再描画を行っています。
- **改善手法**:
  VU メーターコンポーネント内を `<canvas>` 描画に切り替え。React の State ライフサイクルからメーター針の描画ループを分離し、`requestAnimationFrame` を用いて内部バッファ値から対数減衰（イージング）補間を行います。
- **効果とリスク**:
  - **効果**: React 全体のレンダリング負荷が低減され、メイン画面のスクロールやダイヤル操作の引っ掛かりが皆無に。針の振れが 60fps / 120fps で滑らかに動作。
  - **リスク**: **低**（UI コンポーネント内の局所的な差し替えで完結）。

### 2.5 USB DAC 接続時のオートパケットプランニング
- **現状**:
  `UsbDirectEngine.cpp` の Isochronous パケット転送は固定のバッファ構成（1ms / 8 マイクロフレーム）で動作しています。
- **改善手法**:
  USB ディスクリプタの解析結果に基づき、DAC の最大サンプリングレート・対応エンドポイントサイズに合わせて `IsoWriteBuffer` とパケット長を動的に最適チューニングします。
- **効果とリスク**:
  - **効果**: 高負荷時や USB バス混雑時におけるアンダーラン（プチノイズ）の発生確率を極小化。
  - **リスク**: **低**（既存のフェイルセーフ AudioTrack フォールバックが担保）。

## 3. アプローチ ②: 多少の構造転換を伴うが劇的な機能・性能改善が望める手法

```
┌────────────────────────────────────────────────────────────────────────┐
│  アプローチ ②: 構造転換・劇的進化（次世代ハイエンドオーディオ化）     │
├────────────────────────────────────────────────────────────────────────┤
│  1. リサンプラーの C++ (NEON SIMD) 完全移送 ＆ JNI パス半減           │
│  2. Oboe / AAudio C++ 低レイテンシー・排他モードの導入                 │
│  3. Bit-Perfect DSD Native (DoP / DSD Direct) USB 伝送                │
│  4. オーディオコアと WebView の完全マルチプロセス分離 (:player)        │
│  5. ユーザー測定 IR 対応（REW 連携・パーティション畳み込み Room EQ）    │
└────────────────────────────────────────────────────────────────────────┘
```

### 3.1 リサンプラーの C++ (ARM NEON SIMD) 完全移送 ＆ JNI パス半減
- **概要**:
  現在：
  `MediaCodecDecoder` (Java) ➔ `RateConverter` (Java: 96kHz化) ➔ JNI (大量データ転送) ➔ `NativeAudioEngine` (C++)
  を、
  **`MediaCodecDecoder` (Java) ➔ 生PCM (44.1k/48k) をそのまま JNI 経由で C++ へ ➔ C++ 側で NEON SIMD スプライン補間 ➔ 96kHz DSP**
  へ再構築します。
- **劇的なメリット**:
  - JNI 境界を通過するオーディオデータ量が **50% 以下に半減**。
  - ARM NEON の 128-bit ベクトル演算器を活用し、4 サンプル並列で補間計算を行うため、リサンプリングの計算コストが実質ゼロ近くまで縮小。
  - オーディオ再生スレッド全体の CPU 負荷が 30% 以上低減。
- **必要な構造転換**:
  - `NativeDspChain.java` の JNI シグネチャを生レート受信用に拡張。
  - C++ 側に `RateConverter.h/cpp` を移植し、既存の位相スナップ（resetPhase, flush）を再現。

### 3.2 Oboe / AAudio C++ ネイティブシンクの導入（AudioTrack の完全脱却）
- **概要**:
  現在、USB 非接続時の出力は Java の `android.media.AudioTrack` を使用しています。これを Google 推奨のハイパフォーマンス C++ オーディオライブラリ **Oboe (AAudio 排他モード)** に切り替え、C++ DSP エンジンから直接ハードウェア出力へ流します。
- **劇的なメリット**:
  - Android OS のミキサー（AudioFlinger）による中間レイテンシーが **50ms〜100ms から 10ms 未満（MMAP 対応機なら 5ms 前後）に短縮**。
  - ボリュームノブの操作、EQ 切替、一時停止、シークの反応が「機械のつまみを直接触っているかのようなゼロ遅延レスポンス」へ進化。
- **必要な構造転換**:
  - `build.gradle` に Oboe NDK 依存関係を追加。
  - `SinkCarrier` を C++ 側の Oboe Stream 保持構造へ再設計。

### 3.3 Bit-Perfect DSD Native / DoP (DSD over PCM) USB 伝送
- **概要**:
  現在 DSD (`.dsf`, `.dff`) 音源は、`DsfDecoderV2` で PCM にソフトウェアデコードしてから再生しています。外付け USB DAC が DSD に対応している場合、**DoP (DSD over PCM) または Native DSD ビットストリームをそのまま DAC に伝送するモード** を `UsbDirectEngine` に実装します。
- **劇的なメリット**:
  - DSD 音源（2.8MHz / 5.6MHz / 11.2MHz）を一切の PCM 変換なしに、100% ネイティブの 1-bit DSD のまま DAC の DA 変換チップへ届けることが可能に。
  - 高級 DAC 側の表示窓に「DSD」インジケーターが点灯し、本格的なスタジオマスター品質のダイレクト再生を実現。
- **必要な構造転換**:
  - `UsbDirectEngine.cpp` に DoP パッキング（0x05 / 0xFA マーカー付与）および DSD raw URB 送信パスを追加。

### 3.4 オーディオコアと WebView の完全マルチプロセス分離 (`:player` プロセス)
- **概要**:
  `AndroidManifest.xml` で `PlaybackService` に `android:process=":player"` を指定し、オーディオ再生エンジン・ネットワークサーバー（OpenHome/DMR）を **独立した OS プロセス** として切り離します。WebView は純粋なリモコン UI としてプロセス間通信（IPC / AIDL または Messenger）で繋ぎます。
- **劇的なメリット**:
  - WebView のメモリ使用量や画面の再描画、万が一のクラッシュが、**再生中の音楽に物理的に一切影響しなくなる**。
  - 画面を閉じても、ブラウザ側のリソースが破棄されても、バックグラウンド再生や OpenHome / DLNA レンダラーが鉄壁の安定性で鳴り続ける。
- **必要な構造転換**:
  - `DlnaPlaybackPlugin` と `PlaybackService` 間の通信をプロセス間通信（AIDL）に再設計。

### 3.5 ユーザー測定 IR に対応した Room EQ（室内音響補正・カスタム畳み込み）
- **概要**:
  現在 Ambience は固定の 4 種類の IR (WAV) のみですが、C++ の FIR 畳み込みエンジンを拡張し、ユーザーが REW (Room EQ Wizard) 等のマイク測定で作成したカスタム補正インパルス応答（WAV）を読み込めるようにします。
- **劇的なメリット**:
  - スピーカー再生時に、自室の定在波や反響を物理的に打ち消す「本格的な Room Correction（室内音響補正）」が利用可能に。
  - CamillaDSP のコアな強みであった「ルームチューニング機能」が Android アプリ単体で完結。
- **必要な構造転換**:
  - 16,384〜65,536 タップの長尺インパルス応答を高速処理するための「均一パーティション FFT 畳み込み（UPOLS）」を C++ に実装。

## 5. 開発スコープの戦略的決定（モバイル特化とフェーズ方針）

2026-09-27 の検討に基づき、プロダクトの用途とリスク対効果（ROI）を総合評価した結果、**本 Android 版アプリは「Phase 1」の完遂へ全力を集中する** 方針を正式決定しました。

### 5.1 スコープ決定の論理的根拠
1. **Phase 3 の切り分け（Linux 据え置き版へ移譲）**:
   - DoP / DSD Native ビットパーフェクト伝送や、REW 測定に基づく長尺 FIR Room Correction（室内音響補正）は、Linux OS 上で展開するデスクトップ・据え置き別アプリにて実装する。
   - 本 Android 版アプリは「**ポータブル・モバイルオーディオ用途**」へ特化させ、過剰に重厚な据え置き向け機能を削ぎ落とすことで、アプリの軽快さと信頼性を最大化する。
2. **Phase 2 の温存（別バージョン・実験的ブランチへ）**:
   - **Oboe / AAudio 排他モード**: Google Pixel 以外の多様な Android 端末（Xiaomi, OPPO, MediaTek SoC 機等）においてドライバレベルでのクラッシュや、Bluetooth / 電話着信時の切断トラブルなど、端末依存の地雷リスクが極めて高い。
   - **リサンプラー C++ 移送**: P0〜P2 で完成させた Java 側 `SinkCarrier` / `RateConverter` の精密なギャップレス境界ハンドオーバーを C++ 側で再構築する必要があり、クリックノイズや曲間ギャップが再発するリスクが高い。
   - したがって、Phase 2 は本番ラインから切り離し、将来の別バージョン開発として温存する。
3. **結論: Phase 1 への集中**:
   - 既存の安定したオーディオコア・再生パイプラインを 1 行も破壊することなく、**局所的チューニング（1〜2 ファイル単位）で完結する Phase 1 のみを採択** する。

2. **モバイル特有の弱点（発熱・バッテリー）の解消**:
   - `RateConverter` のテーブル化による Java CPU 負荷半減
   - VU メーター描画ループの React レンダリング分離
   - これらにより、長時間の再生でも端末が熱くならず、バッテリー消費を大幅に抑制
3. **安全な段階的ロールアウト**:
   - 各施策が 1〜2 ファイルの独立した改修であるため、Git コミットを項目ごとに分けることで、万が一意図しない挙動があってもその項目だけを即座に revert（ロールバック）可能。

### 7.1 【最重要】ビルドが壊れていた（Phase 0）

### 7.2 RateConverter テーブル化: 測定により**効果が逆符号**

文書 2.1 およびマトリクス①-1 は「CPU 負荷 40〜60% 削減・音響特性 100% 維持」と記載していますが、**JVM 21 で実測したところ再現しませんでした**。

**測定 1: 速度**（現行 `catmull` 4 点補間 vs 512 タップ LUT、2 回測定）

| 方式 | 実行時間 |
|---|---:|
| 現行 Catmull-Rom | 12.10 / 12.80 ns/sample |
| 512 タップ LUT（文書提案） | 12.54 / 13.23 ns/sample |
| 削減率 | **−6.5% / +3.3%**（測定間差はあるが、方向は「同等〜遅い」） |

**測定 2: バイト完全性**（1kHz サイン 10 秒、float32 出力で比較）

- **bit 一致率 78.07%**、最大誤差 **5.96e-08**
- 参考: float32 の 0.5 における 1 ULP = 2.98e-08 → 誤差は **2 ULP**

**根本原因**は `posFrac += step` による**浮動小数点ドリフト**です。44.1kHz で 2,000 万サンプルをシミュレートしたところ、`posFrac` の distinct 値は **20,000,000 個**でした（周期 320 が全く成立しません）。したがって:

- 有限タップ LUT は位相を**量子化**するため、出力は原理的に **100% 一致しません**
- 文書の核心である「**線形位相・ゼロプリリンギングを 100% 維持**」は、**512 タップ量子化では達成不可能です**

**判定**: 「低リスク」項目として実施すると **CPU 負荷を増やさ、かつ音響特性を僅かに劣化**します。**Phase 1 からの除外が正しい判断**であり、本節の測定がその根拠です。
なお「厳密周期テーブル」「double ビットキャッシュ」の代替案も実測で**高速化にならない**ことを確認済みです（キャッシュは 12.7% 遅化）。正攻法は C++/NEON 化であり、これは既に Phase 2（①-1 保留）に位置付けられています。

### 7.3 VU メーター:「現状」の記述が実態と異なっていた

文書 2.4 は「100ms ごとに届く `playbackTime` イベントで React の State 更新を行い」と記載していますが、**実態は異なります**。

- `src/App.tsx` のポーリングは既に **`requestAnimationFrame`**（`App.tsx:480-496`）で **60fps** 実行済みです。「100ms → 60fps 化」による負荷低減は**すでに達成済み**であり、Canvas 化の主眼（描画負荷）は発生しません。
- **真の問題は 7.4 に示す実バグ**でした。
- 「TSX 1 ファイルのみ・リスクゼロ」という見積もりも成立しません。`peakLevels` は **`App.tsx` の State** のため、毎フレーム **`App` 全体が再レンダリング**されます（`AudioChassis` → `PlayerControls` を含む）。VuMeter.tsx 単体を Canvas 化しても **App 本体の再レンダリングは止まりません**。

### 7.4 VU メーター: 実バグを特定し修正（Phase 3）

#### (a) bit-perfect モードでメーターが音量を過小表示していた（実バグ）

**経路間でボリューム段の位置が不一致**でした。

- **DSP 経路**: `getPreMasterPeaks()` は**マスターステージ前**の計測（`NativeAudioEngine.cpp:327-335`。ボリューム適用は 346 行目）。よって Java 側の `currentMasterVolume` 乗算は**正しい**です。
- **bit-perfect USB 経路**: **ボリューム段が原理的に存在しない**（フルスケール出力）にもかかわらず、`maybeNotifyProgress()` が**依然 `currentMasterVolume` を掛けていました**。

結果として、**音はフルスケールで出力しているのにメーターだけ音量倍で沈む**という状態でした（同一楽曲でモード間で表示が食い違う）。
→ `peaksArePostFader` フラグを追加し、bit-perfect 経路のみ乗算をスキップ。

#### (b) ピークホールド不在によりトランジェントが視認できなかった

- Java 側は **100ms 窓**（`maybeNotifyProgress` の `now - lastNotifyMs <= 100`）で **10Hz** 送信、JS 側は **60fps** で受信します。
- 窓ごとに値が 0 に戻るため、**ピークが点滅**して見えていました。
- **1.5 秒のピークホールド**（チャンネル別独立）を追加しました。再生開始時と `seek()` でリセットし、前の曲の残像やシーク直後のゴースト表示を防ぎます。`seek()` は制御スレッドから触るため対象フィールドは `volatile` にしています。

#### (c) 表示スケールの再校正（実測に基づく）

旧 `pow(x, 0.7)` では不足していたのは**曲線ではなくスケールの終端**です。線形振幅スケールでは振幅の大部分が上端数 % に集中するため、リスニング音量（ボリュームは `(level/max)²`）では、適正マスタリングされたトラックのピークでも `-7 dBFS` 程度に留まり、棒の上端に届きません。**dBFS ベース（-30〜0 dBFS = 1.5dB/セグメント）**へ置換しました。

実測（マスタリング済みトラックのピーク 0.90 を想定）:

| 音量/12 | ピーク | 旧 | 新 |
|---|---|---|---|
| 6 | −13.0 dBFS | 35%（7 seg） | **57%（11 seg）** |
| 8 | −8.0 dBFS | 53%（11 seg） | **73%（15 seg）** |
| 10 | −4.1 dBFS | 72%（14 seg） | **86%（17 seg）** |
| 12 | −0.9 dBFS | 93% | **97%（19 seg）** |

これにより**赤は -4.5 dBFS 以上**のみで点灯となり、「音量が大きい」のではなく「**本当に熱い**」状態のみが赤になります。異常入力（0 / 負値 / NaN / Infinity / denormal / 1 超）も全て 0..1 に収まることを確認済みです。

### 7.5 保留 3 項目の再見積もり

- **①-1 VU メーター Canvas 化**: 7.3 のとおり「VuMeter.tsx のみ」では App 全体の再レンダリングを停止できず、**配線範囲が広がります**。ピークホールド導入（7.4b）により値の変化が緩やかになったため、優先度はさらに下がっています。
- **①-2 メタデータディスク永続化**: 前提が異なります。`MusicBrainzClient` / `WikipediaClient` の `LruCache<>(100)` は **URL キーの API レスポンス（JSON）**のみで、**アルバムアートは含みません**（アートは `AlbumArtProvider` の `LruCache<String,byte[]>` という別系統）。また両クライアントは `Context` を持たない static 実例のため、`getCacheDir()` を得るには **Context 注入の配線**が必要です。**工数は文書の「2 クラス・4〜6 時間」の約 2 倍**と再見積もりすべきです。
- **①-4 RateConverter テーブル化**: 7.2 のとおり**不実施**が妥当です。

### 7.8 設計中の host テストが検出した実バグ（Phase 2）

USB ガードの設計の過程で、**新規に書いた host テストが潜在的なバグを 1 件検出**しました。

- `isoMaxPacketBytes()` は**切り捨て（floor）**でパケットサイズを算出しますが、`buildIsoPlan()` は**分数キャリーを加算してから除算**するため、実際のパケットは floor 値より**1 フレーム大きい**です（44.1kHz/1ms → 45 フレーム、not 44）。
- 当初 floor 値でガードを実装すると、**ちょうど 1 フレーム大きすぎる計画を見 통과させる**（すなわちガードが無意味になる）状態でした。
- 対策: 真の worst case となる `isoMaxPacketBytesCeil()` を追加し、ガードにはそちらを使用しました。境界値（容量がちょうど一致するエンドポイントは受理、1 バイト足りない場合は拒否）もテストで固定しています。

また `wMaxPacketSize` は **HIGH/SUPER 速度ではマイクロフレーム単位**、**FULL 速度ではミリ秒単位**という USB 2.0 仕様の解釈差があり、これを `isoEndpointCapacityBytes()` に実装しました。容量が不明（0）の場合は**拒否しない**設計です（常時発動すると全 DAC が AudioTrack にフォールバックしてしまうため）。
